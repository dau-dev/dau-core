dau_core.element_types¶

Element types: what a value IS, not how wide it is.

A registry parameter that says 32 says a field is 32 bits. It does not say whether those bits are a signed integer, a Q16.16 fixed-point number or an IEEE-754 binary32 – three things a tile must treat differently and which a width cannot distinguish. This module gives the palette’s element types names (“int32”, “q16.16”, “float64”) and turns them into the single integer a SystemVerilog parameter can carry.

THE ENCODING is stated in dau_core/hdl/types.svh and mirrored here, because Verilog cannot read Python and the registry cannot read a header. test_element_types.py holds the two to the same numbers.

[7:0] total width in bits (1..255) [15:8] fractional bits (0 for integers and for floats) [16] 1 = IEEE-754 binary floating point [17] 1 = unsigned

A PLAIN SIGNED INTEGER ENCODES AS ITS OWN WIDTH, so int32 is 32 – the number the palette already carried. Migrating a parameter from a width to a type therefore changes no synthesized bit, no measured envelope, and no staged design; only the types a width could never express encode to anything new. It is also why a bare integer stays a legal spelling: a caller who means “a signed integer this many bits wide”, or who wants a width the palette has no name for, writes the number.

dau_core.element_types.element_type(value: int | str) → ElementType[source]¶

The element type a declared value names, in either accepted form.

A STRING is a type spelling. An INTEGER is the encoding – which, for a plain signed integer, IS its width, so 16 still means int16 and is the only integer form worth hand-writing. There is deliberately ONE interpretation of an integer here, and it is the same one the RTL applies to the parameter it receives: a Python side that read 16 as a width while Verilog read it as a code would be the exact confusion this module exists to end.
