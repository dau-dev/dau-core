dau_core.capability_contract¶

Composition-derived capability contract: the single source of truth for what a generated shell can do.

capability_contract(spec) derives the contract from the same ScanCompositionSpec that generates the shell top, using the registry’s declared HDL facts (opcodes, input types, count ports, contract kinds, row capacities). Three consumers read it:

  • the identity register block (operator_bitmap / lane_count / host_opcode_bitmap / sort_capacity words, register map 0.2);

  • the shell-build artlink manifest (to_mapping(), JSON-able);

  • host planners (to_design() for the pushdown scheduler, driver capability decode via the manifest mapping).

Hardware truth vs protocol truth is explicit: operator_bitmap carries only OperationCodes some tile executes in HDL (MIN/MAX/SUM/COUNT); AVERAGE is never a hardware opcode — when a tile provides both SUM and COUNT it appears in host_opcodes (the host divides the results at protocol level), never in opcodes.

dau_core.capability_contract.capability_contract(spec: dau_core.composition.ScanCompositionSpec) → CapabilityContract[source]¶

Derive the capability contract from the composition that generates the shell top — same spec, same registry, one source of truth.

reconfigurable stays false: the generated walker binds every config port to the literal the composition names, so no composed design has runtime config registers yet. When the generator can bind them to registers, the composition will say so and this is where the contract reads it.
