Square root of a Q``(32-f)``.``f`` fixed-point value, EXACTLY.

A fixed-point root is an integer root in disguise. With x = X * 2**-f, the result sqrt(x) * 2**f is sqrt(X * 2**f) — so the answer is isqrt(X << f), floor-truncated like every other fixed-point result in this package (the multiply-shift convention).

class dau_core.operators.MembershipBuildSet(/, **data: Any)[source]¶

Bases: dau_core.models.CheckedModel

The membership memory: a direct-mapped EXACT bitmap over the configured dictionary-id key space [0, key_space). Key k is a member iff 0 <= k < key_space and bit k is set.

Addressing decision (and its exactness). The IN-list / semi-join key column is dictionary-encoded host-side (dau-polars) into dense ids [0, N), and key_space is that dictionary’s cardinality rounded up to a multiple of 64. Because every id maps to exactly one bit, membership is EXACT — no false positives AND no false negatives — over the id space. A full 2**32 bitmap would be 512 MB, impossible; the bounded dictionary space is the natural fit and keeps the whole memory BRAM-resident. A probe key outside [0, key_space) is definitionally a non-member: the build set only ever holds in-range dictionary ids, so an out-of-range probe key (signed int32, so negatives and ids >= key_space included) cannot be in it. This is the honest, verifiable v0; MembershipKind.BLOOM is the future inexact alternative for unbounded key spaces (host-verified false positives).

The bitmap loads as key_space // 64 little-endian 64-bit image words: word w bit b is id 64*w + b.

Golden semantics for the keyed state tile: a per-key accumulator updated once per row, emitting the POST-UPDATE state for every row.

This is the primitive the stateful family is built on. Unlike every tile that precedes it, the output for a row depends on rows that came before it with the SAME key — a loop-carried dependency per key, which is exactly the shape a SIMD CPU cannot vectorize and a spatial datapath can hold on-chip.

rows are (key, value) pairs in arrival order. Each row reads its key’s current state, applies op, writes it back, and emits (key, new_state). A key seen for the first time starts from initial, so the first row of a key emits op(initial, value) — NOT value, unless op is SET. That distinction is the whole reason initial is explicit rather than implied.

Emitting post-update state, not pre-update, is a deliberate contract. Post-update is what a running aggregate means, it is what the hardware can produce without an extra pipeline stage holding the old value, and it makes back-to-back same-key rows well defined: the second row observes the first row’s write. In hardware that is a read-modify-write hazard the tile must FORWARD rather than stall, and this golden pins the answer it must forward to.

capacity is the declared number of distinct keys the table holds. It is a hardware fact (a BRAM depth), so exceeding it is an ERROR rather than an eviction: silently dropping a key would make the result wrong in a way no downstream consumer could detect. Rows already emitted stay emitted, and the error is returned alongside them so a caller can see exactly where the table filled.

Hardware note the HDL must honour: exact arbitrary-key lookup at one row per cycle needs a CAM or a pipelined associative/hash design with collision handling and pending-allocation tracking. A plain single-BRAM dictionary cannot do it, and the forwarding above must bypass both the newest in-flight update and a pending key allocation.

initial=0 is unambiguous but worth stating: MAX over only negative values emits 0, and MIN over only positive values emits 0. Callers wanting the first value to win should pass the domain’s extreme.

Golden semantics for the HASH-mode grouped field-sum aggregation tile: one INT64 accumulator set per DISTINCT key in a bounded on-chip table, drained key-ascending at close-out.

The difference from grouped_field_sum_rows() is the whole point of the tile: the ordered tile groups CONSECUTIVE equal keys, so a key that reappears after another key opens a second partial group the host must merge, and the staged table must be pre-sorted on the group key. This tile holds a per-key accumulator, so input order does not matter and a key may reappear anywhere in the batch — one record per distinct key, always. That removes the sorted_by_key staging precondition from every grouped scan.

Two contracts are deliberate and must be honoured bit-for-bit by the HDL:

Emission is key-ASCENDING (signed). A hash table has no intrinsic order, so leaking the probe/slot order into the record stream would make the result depend on the hash function — an implementation detail no golden could pin and no host could rely on. Sorting the drain by signed key makes the order implementation-independent and physically true (the session-gap tile’s min-extraction drain is the same decision).

Overflow is an ERROR that invalidates the batch, never an eviction. capacity is a hardware fact (the table depth). When a row presents a key not in the table and the table is full, the batch reports GROUP_CAPACITY_EXCEEDED and returns NO groups: evicting or silently dropping the key would make the answer wrong in a way no downstream consumer could detect, and returning the partial accumulation would be worse than useless — the host’s recovery is to re-run the batch split by key range, so a caller that merged the partial with the re-run results would DOUBLE-COUNT every key that had accumulated before the overflow. Discarding the batch is also the platform’s uniform error convention (an error close-out invalidates the whole batch; the tile’s group_count reads 0 and no success close-out is raised), which is what lets the golden and the HDL agree by construction rather than by inspection. Recovery is exact because INT64 sums and counts are additive per key — see merge_hash_grouped().

field_mask bit i selects field i of the quad row (key, value, aux0, aux1); selecting field 0 sums the key itself, which is legal and equals key * count (the ordered tile’s convention).

Returns (groups_key_ascending, error_code).

dau_core.operators.merge_hash_grouped(partials: collections.abc.Iterable[collections.abc.Iterable[HashGroupedAggregate]]) → list[HashGroupedAggregate][source]¶

Merge per-batch hash-grouped partials into one key-ascending result — the host half of the overflow contract.

Splitting a batch (by key range, or simply into smaller batches) and merging the partials is EXACT: INT64 sums and row counts are additive per key, and no other state crosses a batch boundary. This is what makes GROUP_CAPACITY_EXCEEDED a recoverable condition rather than a failed query, and the property merge(split(rows)) == one_shot(rows) is the test that keeps it honest. Every partial must carry the same field_mask; mixing masks is a caller error, not a merge case.
