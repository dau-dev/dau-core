test_composition.test_a_sized_tile_prices_at_its_size_not_its_default() → None¶

A parameter that changes the hardware has to change the price.

This assertion used to be the OPPOSITE – that a 6M-key membership filter priced identically to a default 4096-key one – and it was true only because the tile carried a scalar envelope that answered every KEY_SPACE with the same numbers. The membership filter is a BITMAP, so its BRAM cost IS the key space: 1 BRAM36 at 4096, 192 at 6,000,000, which is 57% of the Artix’s 335 budgeted blocks. Every composition using the silicon-proven configuration was priced at 1/192 of the BRAM it actually places.

test_composition.test_a_text_recorded_under_an_older_palette_is_refused_by_version_not_by_parse() → None¶

The defect this boundary closes, in one place.

A build manifest written before the width-named tiles were renamed records a canonical text naming them. Reading it against today’s registry raises UnknownCoreError — an error about a missing tile, from a design that is built, flashed and answering. The version prefix beside the text is the fact that says the text predates this palette, and it says so without a parse.

test_composition.test_handle_table_capacity_is_design_identity_and_inert_at_zero() → None¶

A handle table is HARDWARE — a table of flops and a resolve stage in front of the reader — so a design that carries one must not share a cache key with one that does not, and eight slots is not sixteen. Zero is the no-table default: a spec that never mentions it keeps the shape it has today and round-trips unchanged.

A job master of some intermediate width is not hardware anyone builds, and permitting it would mean carrying padding logic through every register slice for a shape with nothing behind it: the AXI-Lite read path zero-extends cleanly at exactly 32 and 64 and needs an explicit pad at anything else.

test_composition.test_a_packed_front_can_feed_a_wide_lane() → None¶

The packed feed and the wide lane compose.

Each is silicon-proven alone and they were mutually exclusive: the wide lane read whole quad rows straight from the reader, so it burned 16 bytes of DDR per row, and the next SLOTS doubling would have demanded 19.2 GB/s from a 12.8 GB/s DDR3. Packed, the same lane demands 9.6.

Two widths are in play and they are NOT the same number. data_width is the READ width – SLOTS packed 64-bit rows per beat – while the lane downstream of the unpacker sees SLOTS whole 128-bit quad rows. Note the consequence: an unpacked SLOTS=8 lane would need data_width=1024, which is not a legal tier, so packing is what puts eight slots in reach at all.

test_composition.test_a_packed_wide_feed_rates_at_the_unpacker_not_at_one_row() → None¶

The packed feed’s ceiling is the READER’s packed-row supply, which is data_width/64, not a flat one row per cycle.

The flat cap read the packed path as “one 8-byte row per 64-bit beat”, true only while data_width was 64. A packed WIDE feed hands the unpacker data_width/64 packed rows per beat, and capping at 1 under-reported the silicon-measured eight-slot lane by 8x – the design would have been priced as no faster than the build it replaced.

test_composition.test_shell_infrastructure_is_selected_by_role_not_by_name() → None¶

Composition IS the registry: the shell cores a composition places are the ones declaring each infrastructure role, exactly one per role, and composition.py names none of them. The order the scan roles are placed in is pinned because core_names feeds the canonical hash.
